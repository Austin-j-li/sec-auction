# Lane A: is the VM's uncommitted work captured by ae03c85?

## Verdict

**No, not fully — but the gaps are already known and self-documented, and nothing looks silently lost.**

- The laptop recovery (`ae03c85`, read as `recovery-tree`) is not a byte copy of the VM tree; it is a reconstruction from Claude-transcript evidence, done by a team of sub-agents (see `_dev/recovery/GAP.md` and `RESTORED_PACKETS.md`, both only in `recovery-tree`). Those two files are themselves an honest inventory of what could and could not be recovered, and the current diff matches that inventory closely — I did not find an undocumented loss.
- **VM has ~889 files (150 paths) that recovery lacks entirely**, plus 80 shared files that differ in content. Of the "only on VM" files, the large majority are exactly the items `GAP.md`/`RESTORED_PACKETS.md` mark `missing`/`Rebuild`/`Lost`: maintenance evidence (screenshots, PDFs, patches, `analysis/` breakdowns), the 2026‑09‑26 run-trial packet (grading, blinded packets, Pro-review dispatch), cockpit runtime state (`_dev/cockpit/state/*.sqlite3`, jobs, lookups — live DB, not source), and `_dev/runs` (empty). A smaller but real set is genuine unrecovered work product: root `HANDOFF.md` (see below), `_dev/maintenance/2026-09-25-staleness-cleanse/` (2 files, marked "Lost, none" in GAP.md), and most of `2026-09-24-bid-terms-taxonomy/` (draft2, contract, dispositions, review docs — marked `missing` in RESTORED_PACKETS.md).
- **Recovery has 6 files VM lacks**: its own `_dev/recovery/` reconstruction log (expected — it's the recovery team's own paper trail), and 5 `.xlsx` workbooks (`datalink/mac-gray/providence-worcester/stec/synacor.xlsx`) under `_dev/reviews/2026-09-26-v1141-retest/`. VM's copy of that same folder instead holds the *derived* per-deal `analysis/<deal>/{bids,deal,rounds,participation,other_scope}.csv` + `manifest.json` breakdowns for those same five deals, but not the raw workbooks. So each side holds a different artifact of the same five-deal retest — recovery has the workbooks, VM has the derived analysis. Neither side has both.
- **80 files that exist on both sides differ**, and the direction is mixed, not one-sided:
  - The root instruction file itself is the sharpest case: VM's live file is **v1.13.2** (21 Sep, frozen); recovery's is **v1.14.1** (26 Sep). Consistent, documented, not a gap.
  - Most `_dev/tools/*.py` and `_dev/tools/cockpit/*` files are substantially larger/different on the VM (e.g. `test_cockpit_workspace.py` 683 vs 307 lines, `workspace.py` 999 vs 807, `verify_catalog.py` 197 vs 136, `diff_workbooks.py` 349 vs 231). These match GAP.md §3–4's own "Near"/"Rebuild" classification: the cockpit application and several offline tools were reconstructed from transcript fragments, not full reads, so the recovered code is a best-effort approximation, not the VM's actual final code.
  - A few files run the other way (recovery larger): `compare_alex.py` (401 vs 396) and `test_compare_alex.py`/`test_effort_sweep.py`/`test_review_helpers.py` diverge substantially in both directions — worth a real diff before trusting either as canonical.

## Bottom line

Everything flagged here as a VM-only gap is already named in the recovery team's own `GAP.md`/`RESTORED_PACKETS.md` — so nothing is a *surprise* loss. But "documented" isn't "resolved": root `HANDOFF.md`'s doNOTs and hash table, the Astra-verification evidence it cites, the 15 trial workbooks, and most of the cockpit/tooling source are still VM-only or meaningfully rebuilt/approximated on the laptop. Pushing `ae03c85`-descended work to GitLab as "the VM work" would be safe for the instruction-version decision trail and the five retest workbooks, but would leave the cockpit application, several offline tools, and the bulk of 24–26 Sep evidence/maintenance packets unrepresented until the VM is reachable again or someone deliberately re-pulls them.
